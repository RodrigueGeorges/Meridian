One REST API, one JavaScript SDK and three bridges for existing tills. The same code works with every PSP in the catalogue.

Get started

  1. Request sandbox access: you get a mk_test_… test key and demo points of sale.
  2. Install the SDK, or call the REST API with the Authorization: Bearer <key> header.
  3. Start a payment, then trigger a failure in the simulator to see the recovery.
import { Meridian } from '@meridian/sdk';

const meridian = new Meridian({ apiKey: process.env.MERIDIAN_KEY });

const p = await meridian.pay({
  posId: 'pos_paris_02',
  reference: 'CMD-0412',      // your reference: replayable without a double charge
  amount: 2450,               // in cents
  currency: 'EUR',
});
const final = await meridian.waitForFinal(p.posId, p.reference);
// final.state : authorized | declined | cancelled | failed

The five calls

pay, status, cancel, refund, receipt. The SDK handles retries, timeouts and lost responses; waitForFinal waits for the real outcome of the payment.

Payment states: created, pending, authorized, declined, cancelled, failed. A network error never yields failed while the outcome at the PSP is unknown.

Webhooks

Meridian sends the outcome of each payment to your URL. Each delivery is signed in the meridian-signature header and retried up to 12 times with increasing delays if your server does not answer.

// meridian-signature: t=1763812345,v1=<hex>
const [t, v1] = header.split(',').map((x) => x.split('=')[1]);
const expected = createHmac('sha256', WEBHOOK_SECRET)
  .update(`${t}.${rawBody}`).digest('hex');
const ok = timingSafeEqual(Buffer.from(v1, 'hex'), Buffer.from(expected, 'hex'));

Existing tills

A till already integrated with Concert, ZVT or nexo goes through Meridian without a rewrite: see Concert, ZVT and nexo Retailer.

In-store terminal: local API and cloud API

The Meridian agent runs on a store machine and drives the terminal on the local network over Caisse-AP on IP, ZVT or nexo. It exposes the same five calls in two ways:

  • Local API (installed till): http://127.0.0.1:8787/v1/payments…, with the same SDK. Works without internet, signed journal on the machine.
  • Cloud API (online till): the till calls the Meridian API; the agent receives the request over an outbound connection, with no port to open. Plug in the point of sale with PUT /v1/pos/{id}/psp and the edge-terminal module ({"agentId": "store-paris-1"}). GET /v1/edge/agents lists connected agents.
TERMINAL=caisse-ap TERMINAL_HOST=192.168.1.50 TERMINAL_PORT=8888 \
MERIDIAN_URL=https://… MERIDIAN_API_KEY=mk_… MERIDIAN_AGENT_ID=store-paris-1 \
npx tsx apps/edge/src/main.ts

With nexo, the agent also handles the session (TERMINAL_SESSION=1 if the terminal requires a Login), checks the terminal ID, reports a busy terminal (refusal terminal_busy, nothing charged) and, after a lost response, asks the terminal for the status until the real outcome. Agent offline: nothing is sent, and the backup PSP chosen by the merchant takes over. Lost response: the request is replayed with the same key and the agent never restarts the terminal. Accept on the device (Tap to Pay)

With an on-device module, pay returns a device field (the payment’s client secret) while the payment is in progress. The app hands it to the PSP’s SDK on the phone, which reads the card. Meridian follows the outcome server-side, as with a terminal. POST /v1/pos/{id}/device-token returns the SDK connection token; the PSP secret key never leaves Meridian. Status and coding assistants

  • GET /v1/status: response rate and average time for each PSP, public, without volumes. See the status page.
  • /llms.txt: a summary of Meridian and its API for coding assistants.
  • MCP server (packages/mcp): a coding assistant reads the catalogue, points of sale and their PSP, payment state and journal, and runs test payments. Payments with a test key only; no cancel or refund tool.
MERIDIAN_API_KEY=mk_test_… MERIDIAN_URL=https://… npx tsx packages/mcp/src/main.ts

For PSPs

A PSP joins the catalogue by describing its API in a declarative module (JSON), with no code in the engine. The module must declare idempotency and status lookup; it is published after passing the 8 failure scenarios against the PSP’s sandbox. Get the module format.
