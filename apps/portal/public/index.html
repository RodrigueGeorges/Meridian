    Tous les branchements

    Une seule API, quel que soit le branchement.

    Caisse installée ou en ligne, terminal du magasin ou PSP dans le cloud, protocole existant ou nouvelle intégration : les mêmes cinq appels, le même journal signé, la même garantie.

    1. CaisseMeridianPSPTPE

      PSP dans le cloud

      La caisse appelle Meridian, qui pilote le terminal par l'API du PSP.

      Disponible · Stripe Terminal

    2. CaisseAgent du magasinTPE

      Terminal du magasin, en local

      La caisse installée parle à l'agent Meridian du magasin, qui pilote le TPE en Caisse-AP, ZVT ou nexo. Fonctionne sans Internet.

      En validation sur matériel réel

    3. Caisse en ligneMeridianAgent du magasinTPE

      Terminal du magasin, depuis une caisse en ligne

      La caisse SaaS appelle l'API Meridian, qui relaie à l'agent du magasin par une connexion sortante : aucun port à ouvrir.

      En validation sur matériel réel

    4. CaisseMeridianPSP

      Caisse existante, sans développement

      La caisse garde sa trame Concert, ZVT ou nexo : Meridian se présente comme son terminal.

      Disponible en démonstration

    5. ApplicationSDK du PSPMeridian

      Sur le téléphone ou la tablette

      Encaissement sans terminal avec le Tap to Pay du PSP ; Meridian suit et prouve chaque paiement.

      En validation sur matériel réel

    Meridian est-il multi-acquéreur ?

    Non. Meridian est un connecteur et un catalogue : l'éditeur ou le marchand choisit le PSP de chaque caisse dans le catalogue et le branche, avec un PSP de secours facultatif utilisé seulement si le premier est injoignable. Meridian ne choisit jamais le PSP à la place du marchand.

    Pour les éditeurs de caisses et de bornes

    Ne perdez plus une vente à cause du PSP du marchand.

    Chaque marchand arrive avec son PSP. Chaque PSP coûte une intégration, une certification et de la maintenance. Avec Meridian, vous intégrez une fois et proposez tout le catalogue.

    Cinq appels. Pas un de plus.

    payer, état, annuler, rembourser, reçu. Le SDK gère les rejeux, les délais et les réponses perdues. Votre code ne connaît pas le PSP.

    // npm i @meridian/sdk
const m = new Meridian({ apiKey, posId });

await m.pay({ reference: 'T-1042', amount: 2450, currency: 'EUR' });
const p = await m.waitForFinal('T-1042');
// p.state → 'authorized' | 'declined' | 'cancelled'
const r = await m.receipt('T-1042');   // ticket + preuve

    Un module déclaratif, pas un projet.

    Vous décrivez votre API dans un fichier : étapes, clés d'idempotence, lecture d'état, codes de refus. Aucun code dans le moteur. Le module est refusé s'il ne garantit pas l'idempotence.

    {
  "id": "votre-psp",
  "countries": ["FR", "BE", "DE"],
  "pay": [
    { "id": "create", "method": "POST", "path": "/payments",
      "idempotency": "{reference}:create" }
  ],
  "lookup": { "path": "/payments/{vars.id}" },
  "declineCodes": ["card_declined"]
}

    La conformité se prouve, elle ne se déclare pas.

    Votre module passe les huit scénarios de panne contre votre sandbox : réponse perdue, coupure réseau, crash, annulation tardive. Le rapport est la condition de publication.
