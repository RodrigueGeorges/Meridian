    Le problème

    Aujourd'hui, chaque PSP est un projet d'intégration.

    Un marchand arrive avec son PSP. Vous ne l'avez pas intégré : la vente est perdue, ou c'est trois mois de développement et une certification.

    Avec Meridian, le PSP est dans le catalogue. Vous le choisissez dans la console, sans une ligne de code.

    Le réseau coupe pendant l'autorisation. La caisse affiche « échec », le client repaie, et vous gérez le litige de double débit.

    Meridian garde le paiement « en cours », retrouve l'issue réelle chez le PSP, et ne débite qu'une fois.

    Vous ouvrez l'Allemagne ou la Belgique. Nouveaux protocoles, nouveaux moyens de paiement locaux, nouveau projet.

    ZVT, nexo, girocard, Bancontact, TWINT : déjà pris en charge, pays par pays.

    Questions fréquentes

    Ce que les équipes paiement nous demandent.

    Meridian est-il un établissement de paiement ?

    Non. Meridian est un prestataire technique : il ne détient pas de fonds et ne signe pas de contrat avec les marchands. Les paiements sont exécutés par le PSP choisi par le marchand, sous son propre agrément.

    Les données de carte passent-elles par Meridian ?

    Non. La carte est lue par le terminal et traitée par le PSP. Meridian ne reçoit que le résultat, la marque et les 4 derniers chiffres pour le ticket.

    Que se passe-t-il si Meridian tombe ?

    Plusieurs instances partagent le même journal. Si l'une tombe en plein paiement, une autre reprend depuis la dernière étape écrite et retrouve l'issue réelle chez le PSP. Le test est public.

    Mes caisses Concert ou ZVT doivent-elles changer ?

    Non. Vous pointez la caisse vers Meridian au lieu du terminal ; les messages restent les mêmes.

    Quels PSP sont disponibles ?

    Stripe Terminal aujourd'hui, en sandbox. Chaque nouveau PSP arrive sous forme de module déclaratif, publié après avoir passé les huit scénarios de panne.

    Qui paie, et comment ?

    L'éditeur, par terminal actif et par mois, comme un outil de son logiciel. Le marchand ne paie rien de plus à Meridian ; sa commission reste chez son PSP.

    Un module déclaratif, pas un projet.

    Vous décrivez votre API dans un fichier : étapes, clés d'idempotence, lecture d'état, codes de refus. Aucun code dans le moteur. Le module est refusé s'il ne garantit pas l'idempotence.

    {
  "id": "votre-psp",
  "countries": ["FR", "BE", "DE"],
  "pay": [
    { "id": "create", "method": "POST", "path": "/payments",
      "idempotency": "{reference}:create" }
  ],
  "lookup": { "path": "/payments/{vars.id}" },
  "declineCodes": ["card_declined"]
}

    La conformité se prouve, elle ne se déclare pas.

    Votre module passe les huit scénarios de panne contre votre sandbox : réponse perdue, coupure réseau, crash, annulation tardive. Le rapport est la condition de publication.
